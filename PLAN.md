## Этап 2. Тесты для persistence — в работе

### Текущий прогресс

- В SQLite `Save` добавлена проверка следующей последовательной высоты с `persistence.InvalidHeightError`.
- `testutil.OpenTestSQLiteDB` принимает путь к миграциям снаружи: тесты и `cmd/zxcoin` запускаются с разными рабочими директориями.
- В `adapters/persistence/sqlite/block_test.go` написаны:
  - `TestSave`: сохранение пустого блока на следующей высоте, проверка хеша заголовка и высоты через `Tip`.
  - `TestSave_InvalidHeight`: отказ при пропуске высоты, проверка полей ошибки и неизменности вершины.
  - `TestSave_RepeatedHeight`: отказ при занятой высоте, проверка полей ошибки и неизменности вершины.

### Следующий шаг

- Сохранение блока с транзакциями и чтение обратно: совпадают поля заголовка, `CoinbaseHeight`, подписи, порядок транзакций, входов и выходов, хеши транзакций. Совпадение только хеша заголовка не доказывает правильное восстановление тела блока.

### Оставшиеся проверки

- Сохранённый блок доступен через `FindByHash`, `FindByHeight`, `Tip` и `List`; проверить границы и лимит списка, отсутствие искомого блока.
- После `Save` выходы видны через `FindByID`/`FindByOwner`; после расходования исчезают из обоих методов, непотраченные остаются, новые появляются. Не полагаться на порядок результатов `FindByOwner`, если он не задан контрактом.
- Ошибка после начала записи не оставляет частично сохранённого блока, транзакций или изменений UTXO. Отказ по высоте происходит до вставок и откат записи не проверяет.
- Для SQLite: сохранность блока и UTXO после закрытия и повторного открытия файловой тестовой БД.
- Общий контрактный набор для SQLite и inmemory пока не выделен. Проверки поведения должны быть общими, подготовка и освобождение ресурсов — специфичными для реализации; каждый сценарий получает независимое хранилище.
- После всех миграций SQLite уже содержит генезис на высоте `0`, поэтому первый новый блок сохраняется на высоте `1`. Для общего набора начальное состояние inmemory должно соответствовать SQLite; штатную мигрированную БД не считать пустой.
- Миграция `000001_create_utxos` создаёт таблицу `utxos`, тогда как SQLite-UTXO вычисляются из `outputs`/`inputs`. Решить, нужна ли эта таблица.

## Этап 3. Правила консенсуса в `verifyTransactions` (`app/blockchain/service.go:190`)

- Coinbase сейчас определяется по признаку «нет входов, 1 выход, сумма == награда». Поле `CoinbaseHeight` при этом не проверяется. Что будет с блоком, в котором coinbase повторяет `CoinbaseHeight` из прошлого блока (подумай про хеш и PK в `transactions`)? А с блоком вообще без coinbase?
- Где по правилам должна стоять coinbase в блоке? Сейчас её позиция ни на что не влияет.
- Транзакция внутри блока, которая тратит выход другой транзакции из этого же блока: валидатор смотрит только в репозиторий. Решай, поддерживать такое или явно запретить, и покрой тестом.

## Этап 4. Mempool после нового блока

- `MineAndAddBlock` убирает из пула только свои транзакции. Но `AddBlock` публичный — что станет с транзакциями в пуле, входы которых потратил чужой блок? Подсказка: у `Mempool` уже есть индекс `inputs`.
- `GetPending` проходит по map, поэтому порядок случайный. Это нормально сейчас, но станет важно, когда появятся комиссии.
- `ReservationTracker` у кошелька: когда снимается резерв, если транзакция так и не попала в блок?

## Этап 5. HTTP API и инструменты

- Методы чтения (`FindByHash`, `FindByHeight`, `List`, `Tip`) уже есть, но эндпоинтов для них нет: `GET /blocks`, `/blocks/{hash}`, `/blocks/height/{n}`, `/tip`. DTO для блока уже лежит в `adapters/http/handlers/dto/block.go`.
- Тесты хендлеров через `net/http/httptest`, особенно для ошибок 400/409.
- `cmd/wallet`: проверь, что он работает с HTTP-узлом от начала до конца (создать tx → `POST /transactions` → `POST /mine` → `GET /utxo`).
- Сложность и награда захардкожены (`NewBlockchain(2, 42)` и `(4, 42)`), путь к базе и порт тоже — подумай о конфиге.

## Дальше (по статье Сатоши)

1. Комиссии: разница входов и выходов идёт майнеру, coinbase ≤ награда + комиссии.
2. Динамическая сложность и уменьшение награды по высоте (`CurrentDifficulty`/`CurrentAward` уже вынесены в методы — удобная точка расширения).
3. Канонический формат сериализации для хеша (сейчас он зависит от Go-представления).
4. P2P между узлами и выбор самой длинной цепочки, то есть форки. Для форков схему БД придётся пересмотреть: подумай, что сломается в `UNIQUE (height)`, если на одной высоте окажутся два блока.
