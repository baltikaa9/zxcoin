# zxcoin

Учебная реализация криптовалюты на Go, построенная по мотивам статьи Сатоши Накамото
[«Bitcoin: A Peer-to-Peer Electronic Cash System»](https://bitcoin.org/bitcoin.pdf).

Проект реализует ядро того, что описано в статье: транзакции на основе UTXO,
цифровые подписи, proof-of-work майнинг, дерево Меркла, mempool и награду
майнерам (coinbase) — с защитой от двойной траты и полным набором тестов.

## Зачем это нужно

Это не форк Bitcoin Core и не совместимая с реальным Bitcoin сеть — это
самостоятельная, изолированная реализация тех же базовых механизмов, написанная
с нуля ради понимания того, как они работают изнутри.

## Основные концепции

### UTXO — непотраченные выходы транзакций

В отличие от банковского счета с одним числом-балансом, здесь нет понятия
«баланс». Вместо этого существует множество отдельных «конвертов» —
непотраченных выходов транзакций (Unspent Transaction Output, UTXO). Каждый
такой конверт содержит сумму и публичный ключ владельца.

«Баланс» кошелька — это просто сумма всех UTXO, принадлежащих его публичному
ключу. Когда кошелек тратит монеты, он берет один или несколько существующих
UTXO целиком, тратит их полностью и создает новые UTXO взамен: один для
получателя, один — «сдача» — обратно себе.

Реализация: [`utxo/utxo.go`](utxo/utxo.go).

### Транзакции: входы и выходы

Транзакция состоит из:

- **входов (`TxInput`)** — ссылок на существующие UTXO, которые тратятся
  (идентификатор транзакции-источника, индекс выхода, подпись);
- **выходов (`TxOutput`)** — новых «конвертов», создаваемых этой транзакцией.

Сумма входов должна быть не меньше суммы выходов. Транзакция может иметь
несколько входов (чтобы набрать нужную сумму из нескольких UTXO) и несколько
выходов (платеж + сдача).

Реализация: [`transaction/transaction.go`](transaction/transaction.go),
примитив выхода — [`coin/output.go`](coin/output.go).

### Цифровые подписи

Владение монетой доказывается не паролем, а асимметричной криптографией
(ECDSA). У каждого кошелька есть пара ключей: приватный (секретный) и
публичный (открытый). UTXO принадлежит публичному ключу; чтобы его потратить,
нужно подписать транзакцию соответствующим приватным ключом.

Подписать можно только зная приватный ключ; проверить подпись может кто угодно,
зная лишь публичный ключ — вычислить приватный ключ из публичного
вычислительно неосуществимо.

Реализация: [`wallet/wallet.go`](wallet/wallet.go),
[`transaction/transaction.go`](transaction/transaction.go).

### Дерево Меркла

Чтобы заголовок блока компактно и проверяемо отражал все транзакции внутри
него, транзакции хешируются не одним общим хешем, а попарно, слоями, до
единого корня:

```
Hash(A) Hash(B) Hash(C) Hash(D)
   \      /         \      /
   Hash(AB)         Hash(CD)
        \             /
         Root = Hash(AB + CD)
```

Это позволяет доказать, что конкретная транзакция входит в блок, предъявив
всего log₂(N) хешей вместо всех N транзакций (Merkle-путь), и легко обнаружить
любую подмену содержимого блока.

Реализация: [`merkle/node.go`](merkle/node.go).

### Proof-of-Work

Чтобы добавить блок в цепочку, майнер должен найти такое значение `Nonce`,
чтобы хеш заголовка блока начинался с заданного количества нулевых байт
(сложность, `Difficulty`). Единственный способ найти такое значение — перебор:
найти его дорого, а проверить — мгновенно (один хеш).

Это делает переписывание уже принятой истории практически невозможным: чтобы
подменить старый блок, пришлось бы заново майнить его и все последующие блоки,
обгоняя всю остальную сеть.

Реализация: [`block/block.go`](block/block.go).

### Coinbase-транзакция

Единственный способ появления новых монет в системе — специальная
coinbase-транзакция: у нее нет входов, только один выход на адрес майнера,
на сумму текущей награды за блок. Она создается автоматически при сборке
нового блока.

### Двойная трата и защита от нее

Основная задача, которую решает вся конструкция — не дать одну и ту же монету
потратить дважды. Проект защищается от нее на нескольких независимых уровнях:

- **при создании транзакции** — кошелек резервирует выбранные UTXO, чтобы не
  выбрать их повторно для другой транзакции;
- **при валидации отдельной транзакции** — проверяется, что UTXO
  действительно существует, еще не потрачен, и подпись верна;
- **при сборке блока** — отслеживается, чтобы один и тот же UTXO не был
  потрачен дважды разными транзакциями внутри одного блока (в том числе если
  атакующий вручную включит в один блок две конфликтующие транзакции);
- **после подтверждения** — UTXO необратимо удаляется из набора при
  добавлении блока в цепочку, попытка повторно на него сослаться в будущем
  блоке провалится, потому что его уже не существует.

## Архитектура

Проект разбит на пакеты с однонаправленными зависимостями (без циклов):

```
coin            — TxOutput, базовый примитив ценности
  ↓
utxo            — набор непотраченных выходов и их резервирование
  ↓
transaction     — транзакции, входы, подписи, валидация
  ↓        ↓
merkle    wallet     mempool
  ↓        ↓            ↓
block           blockchain
                     ↓
                   main
```

| Пакет | Отвечает за |
|---|---|
| `coin` | Примитив выхода транзакции (`TxOutput`) |
| `utxo` | Хранилище непотраченных выходов, резервирование |
| `transaction` | Транзакции, подписи, проверка валидности |
| `merkle` | Дерево Меркла и корневой хеш |
| `wallet` | Пара ключей, создание подписанных транзакций |
| `mempool` | Пул транзакций, ожидающих включения в блок |
| `block` | Блок, заголовок, майнинг (proof-of-work) |
| `blockchain` | Консенсус: проверка и добавление блоков, награда |
| `testutil` | Общие вспомогательные функции для тестов |

## Как запустить

```bash
go run main.go
```

Демонстрационный сценарий в `main.go` создает два кошелька, генезис-блок,
несколько транзакций между ними и показывает итоговое состояние UTXO.

## Тесты

```bash
go test ./...
```

Тесты покрывают все основные механизмы защиты: двойную трату (между
транзакциями в блоке, внутри одной транзакции, между уже подтвержденным и
новым блоком), поддельную подпись, недостаточный баланс, невалидный
proof-of-work, неверный хеш предыдущего блока и корня дерева Меркла,
дублирующуюся coinbase-транзакцию — а также позитивные сценарии.

## Что не реализовано

Это осознанные упрощения, а не забытые детали:

- **Динамическая сложность.** В реальном Bitcoin сложность подстраивается под
  среднюю скорость нахождения блоков (раз в 2016 блоков). Здесь сложность
  задается статически при создании блокчейна.
- **P2P-сеть.** Вся система работает в одном процессе. Нет узлов, реально
  обменивающихся блоками и транзакциями по сети, а значит нет и практической
  проверки разрешения форков (раздел 5 статьи Сатоши) в реальных сетевых
  условиях.
- **Формат сериализации.** Хеширование транзакций использует внутреннее
  Go-представление структур, а не байт-в-байт совместимый с настоящим Bitcoin
  формат — проект не совместим с реальной сетью Bitcoin и не предназначен для
  этого.
